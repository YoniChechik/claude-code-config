# E2E to Integration Tests Conversion Plan

## Executive Summary

This plan identifies which Playwright E2E tests should be converted to Jest + @testing-library/react integration tests and which should remain as E2E tests. The conversion focuses on tests that validate component behavior in isolation vs. full app flows. Out of 10 E2E test suites, **6 are good candidates for conversion** to faster, more maintainable integration tests. These conversions will improve test speed (5-10x), reduce flakiness, and simplify maintenance while keeping critical cross-browser and full-app flow tests in E2E.

This requires **3 PRs**: (1) Component integration tests, (2) Modal/Modal integration tests, (3) Message rendering tests.

**Current State**: E2E Playwright tests in `e2e/` directory, one integration test in `__tests__/SessionHeader.test.tsx`

**Target State**: Balanced test suite with component tests fast-running locally and E2E tests covering critical user flows

## Architecture

### Integration Test Pattern (established in SessionHeader.test.tsx)
```
1. Mock fetch globally or selectively
2. Render component with testing-library
3. Use fireEvent or userEvent for interactions
4. await waitFor() for async updates (useEffect, API calls)
5. Use act() wrapper for state updates
```

### Mock Strategy for Converted Tests
- **API Mocks**: Use jest.mock() for fetch or axios; return Promise-resolved mock data
- **Component Dependencies**: Mock child components sparingly (only if they're external/heavy)
- **Session/Message Data**: Create factory functions for consistent test data
- **No Playwright routing**: Jest mocks replace page.route() patterns

### Remaining E2E Tests Strategy
- Use Playwright's built-in API mocking (page.route) for realistic streaming
- Test full user journeys requiring tab/window focus (notifications tests with .skip)
- Verify causal ordering and data integrity across streaming
- Ensure browser-specific behaviors (scroll, focus, visibility detection)

## Dependencies & Risks

### Dependencies
- **Jest + @testing-library/react**: Already configured (used in SessionHeader.test.tsx)
- **Mock data factories**: Must be created for consistency (mockData.ts)
- **Component composition**: All components must be testable in isolation with mocks

### Risks

| Risk | Probability | Mitigation |
|------|-------------|-----------|
| Mock data diverges from real backend | Medium | Create factory functions; update when API changes |
| Streaming tests fail if mocking incomplete | Medium | Keep complex streaming scenarios in E2E |
| Component refactoring breaks integration tests | Low | Tests are component-focused; refactors localized |
| E2E test maintenance burden increases | Low | Clarify remaining E2E tests in documentation |
| Flaky scroll/focus tests remain | Low | Already skipped; documented as E2E-only scenarios |

### Mitigation Checklist
- [ ] Create mockData.ts with message, session, tool structures matching backend
- [ ] Verify component props and mock data alignment before PR
- [ ] Run full test suite (jest + playwright) before each PR
- [ ] Document which tests remain E2E and why (comment in spec files)
- [ ] Update CI/CD to run jest tests separately from E2E tests

## Difficulty: EASY-MEDIUM

- **Easy aspects**: Component props are testable; mock API patterns proven in SessionHeader.test.tsx; no complex browser APIs needed for most tests
- **Medium aspects**: Streaming/message mock data structures require careful design; ensuring mock data stays in sync with backend; some tests need creative refactoring to work without full app context

**Time Estimate**: ~2-3 weeks for full conversion (3 PRs, ~50 new test files/updates)

## Assumptions & Notes

1. **Mock data must match API contracts**: Mock session, message, and tool structures must align with real backend responses. Create factory functions to manage this.

2. **Component isolation is feasible**: All converted components should render without full app context (routing, global state). Parent components (ChatPane, SplitLayout) may need props passed instead of pulled from context.

3. **Streaming is an edge case**: Real streaming behavior with chunks, timing, and ordering is inherently E2E. Integration tests focus on component behavior when given final/static message data.

4. **Session state management**: Tests assuming session state (e.g., messages persisting) may need refactoring to pass messages as props rather than relying on parent app state.

5. **Browser focus/visibility APIs**: Tests involving `document.hidden`, `window.focus()`, or cross-tab coordination remain E2E only. These were already problematic (many .skip).

6. **Tool execution**: Tests that verify tool use blocks are rendered correctly are integration tests; tests that verify tool *execution* order and results are E2E.
